# 翻訳をさらに高速化するための調査と提案

## 実装への反映

2026-11-10。PLaMoをChrome内で実行する条件で、未設定時のモデルを0.8Bへ変更した。保存済みの2B選択は保持する。長段落の分割片は最大2片で並列処理し、原文順に表示する。ブラウザ実行ではキャッシュ済みの結果を推論キューの前で返し、同じ原文・モデル・翻訳先の実行中要求を共有する。途中出力とキャンセルは要求ごとに扱い、全要求の取消で実推論を止める。

型検査、323テスト、ビルド、配布物検査が成功した。Chrome 154のWebGPUで0.8Bの訳文生成、同文の推論共有時の個別キャンセル、結果キャッシュの再利用を確認した。検証は現在のengineと配布用WASMをHTTP上で接続したもので、拡張のbackgroundとoffscreen間の通信を含まない。速度の比較測定は行っていない。

GPUの枠数は2枠を維持した。4枠化、別量子化、短文の結合、Attention設定変更、投機的デコードは比較候補として残す。同文の推論を共有した場合の優先度は最初の要求に従う。

以下は実装前の調査と提案であり、記載した候補すべてを実装したものではない。

調査日 2026-11-10。対象は `fcedfa6cb09ee888c1bad7c65aa8d33048c881d0` の翻訳機能。目的は英語のページを日本語で読み始めるまでの待ち時間と、全文の翻訳時間を短くすることだ。

PLaMoを使い、推論をChrome内で完結させることを必須条件とする。通常翻訳とやさしい日本語の両方に適用する。Ollama、ネイティブサービス、Chrome Translator API、別の翻訳モデルへの切替は採用候補に含めない。

初めて読む文章の高速化には、長段落の分割片の並列化、GPUの2枠・4枠比較、入力処理と生成処理の設定調整を優先する。完成済みキャッシュの待機回避と同文の推論共有は、再翻訳や重複文章の待ち時間を減らす補助策として扱う。

1. 現行版にはSakutto由来のWASM最適化まで入っている。GPUの過去比較では明確な改善を確認できておらず、同じ最適化を再提案する段階ではない。
2. 新たに減らせるのは、キャッシュのキュー待ち、同文の重複推論、長段落内の直列処理だ。コードから確認した候補であり、短縮率は未測定である。
3. まず現行PLaMo 2B・Q4_K_Mを固定して処理方式を比較する。PLaMo 0.8Bや別量子化は品質が変わり得るため、別の比較として扱い、自動切替は提案しない。
4. PLaMo同士の投機的デコードは中長期候補とする。Chrome内での互換性とメモリ消費を確かめず、論文の速度倍率をこの拡張に当てはめない。

[前回の調査](translation-performance.md)で提案された途中表示、画面内優先、結果キャッシュ、GPU並列化は実装済みだ。本稿はその後の[WASM最適化](translation-wasm-performance.md)を出発点にする。今回はコードと一次資料の調査であり、新しい速度測定や製品コードの変更は行っていない。

## 現在の処理と測定の限界

ページ翻訳はcontent、background、offscreenを経由して翻訳エンジンへ届く。原文を最大1200文字の分割片にし、段落間は先読みするが、一つの段落の分割片は順番に処理する。ブラウザGPUではモデル未ロード時に最初の1件で準備し、その後は最大2件を同時に開始する。同じモデルをGPUへロード済みなら最初から2件を開始できる。各組の全件が終わってから次を開始する。ブラウザのCPU実行は1件ずつだ。[content.ts](../../features/translate/content.ts)、[engine.ts](../../features/translate/engine.ts)、[scheduler.ts](../../features/translate/scheduler.ts)。

| 対象       | 実装済みの処理                                                                        | まだ確認できていないこと                               |
| ---------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| 表示       | 途中表示、通知を60ms間隔に制限、画面内優先、選択翻訳の待機優先                        | 実ページの最初の訳文表示までの時間と、通信・描画の内訳 |
| キャッシュ | 成功結果100件・合計20万文字、最大5分                                                  | 同時に来た同文の集約、待ち行列を経由しないヒット処理   |
| GPU        | 2枠、合計8192トークン、continuous batching、全文分のSWAキャッシュ                     | 4枠以上での速度・メモリ・選択翻訳への影響              |
| CPU・WASM  | 最大4スレッド、SIMD、bind group再利用、パラメーター一括転送、不要な推論状態の保存停止 | スレッド数の最適値、GPUカーネル単位の律速箇所          |
| モデル     | 2Bと0.8BのQ4_K_M、ロード済みモデルの再利用                                            | 同一文章での品質と速度の比較、別量子化の価値           |

[保存済みの実験](translation-wasm-performance.md)では、GPU・2B・12段落の中央値は旧版5855.5ms、新版5967.1msだった。各5回の範囲は大きく重なり、高速化とは判断されていない。CPU・0.8B・短文2件には短縮の記録があるが、GPUや長文には一般化できない。どちらもbackgroundとoffscreen間の通信を省いた検証で、実ページ全体の時間ではない。

## 既存の翻訳機能から取り入れる候補

### Sakuttoとの差分

Sakuttoの現行ソースは `dc6a5001ac3c751d8436c1e05ab07d67ece2f758` を確認した。並列数の多さだけを移植するより、翻訳対象の分割と結果の戻し方を参考にする価値がある。

| 工夫                         | この拡張への提案                                     | 効果を期待できる条件と制約                                                              |
| ---------------------------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 長文を分割して別ジョブで処理 | 同一段落の分割片もGPUへ投入し、元の順序で表示する    | 長い段落が少数のページ。後半が先に完成しても順序を崩さず、取消・DOM変更を全片に反映する |
| 短いラベルのまとめ処理       | 関連する短い見出しや項目に限定して試す               | 小さな入力が多数ある場合。区切りの消失、訳文の混入、項目数の不一致なら個別翻訳へ戻す    |
| GPU並列数の段階的な縮小      | 2枠と4枠を先に比較し、失敗時に少ない枠で再ロードする | メモリ不足時のCPU移行を減らせる可能性。16枠の一律採用は避ける                           |
| 結果の永続保存と重複集約     | まずメモリ内で実行中の同文を共有する                 | 繰り返し表現が多いページ。永続保存には現在の保存方針の変更が必要                        |
| CPUのスレッド数調整          | 同じ0.8Bで2・4・8スレッドを比較する                  | CPU実行時。物理コア数、メモリ帯域、他タブの応答性によって最適値が変わる                 |

出典はSakuttoの[分割片の処理](https://github.com/jammaru/sakutto/blob/dc6a5001ac3c751d8436c1e05ab07d67ece2f758/src/engine/in-browser/engine.ts)、[短文のまとめ方](https://github.com/jammaru/sakutto/blob/dc6a5001ac3c751d8436c1e05ab07d67ece2f758/src/engine/text/plan.ts)、[キャッシュ](https://github.com/jammaru/sakutto/blob/dc6a5001ac3c751d8436c1e05ab07d67ece2f758/src/engine/cache/caching-engine.ts)、[実行設定](https://github.com/jammaru/sakutto/blob/dc6a5001ac3c751d8436c1e05ab07d67ece2f758/src/engine/in-browser/backend.ts)。同プロジェクトの高速化率を、この端末・モデル・入力での見込み値には使わない。

短文をまとめる処理と、複数の要求を並列に処理することは区別する。前者はモデルに渡す文章の形を変えるので訳文も変わり得る。後者は別々の文章を保ったままGPUの処理をまとめる方式だ。短文の結合は数字、リンク、箇条書きの対応を自動検査できる範囲から試す。

Sakuttoは描画を`requestAnimationFrame`でまとめ、`IntersectionObserver`で画面内の候補を管理し、非表示タブの新規処理を抑える。現行版は通知をすでに60ms間隔に制限しているため、追加効果はDOM更新や候補の位置計算が重いページで測る。非表示タブの停止は全文をバックグラウンドで訳す動作を変えるので任意の設定案とする。[SakuttoのDOM処理](https://github.com/jammaru/sakutto/blob/dc6a5001ac3c751d8436c1e05ab07d67ece2f758/src/dom/session.ts)、[現在の通知処理](../../entrypoints/offscreen/main.ts)。

Immersive Translateは本文の選択・除外、サービス別の送信制限、一回にまとめる文章量を設定できる。現行版にも本文抽出とUI除外はあるため、抽出機能自体を新規追加する提案にはしない。外部APIの待ち時間や送信上限を扱う参考であり、PLaMoの生成速度が上がる根拠にはならない。[公式の詳細設定](https://immersivetranslate.com/docs/advanced/)。クラウド翻訳APIの追加は原文の送信先と費用を変えるため、端末内翻訳を前提とする今回の推奨から外した。

### 他のエンジンから参考にする範囲

Firefox Translations / BergamotやCTranslate2は、量子化や文章の長さに応じたバッチ処理の参考になる。ただし、それらの翻訳モデルへの置換は今回の条件から外れる。Chrome Translator APIもPLaMoを指定して実行する経路ではないため、通常翻訳だけを任せる案も除外する。[Bergamot](https://firefox-source-docs.mozilla.org/toolkit/components/translations/resources/03_bergamot.html)、[CTranslate2の性能設定](https://opennmt.net/CTranslate2/performance.html)、[Translator API](https://developer.chrome.com/docs/ai/translator-api)。

WebLLMはChrome内でWebGPUを使う別ランタイムなので、PLaMoを維持して実行できる場合だけ条件に合う。ただし、PLaMoのモデル構造・重み変換・コンパイルへの対応は未確認だ。現行wllamaの調整より大きな変更になるため、現時点では移行を推奨しない。[WebLLM](https://github.com/mlc-ai/web-llm)。

## LLMの構造から考える高速化

一つの翻訳の待ち時間はおおむね「待ち行列＋必要なモデル準備＋入力処理＋訳文生成＋通信・描画」に分けられる。ページ全体では各段落が重なるため、これらの時間を単純に全件分足した値にはならない。

入力をまとめて処理する段階をprefill、訳文を順に生成する段階をdecodeと呼ぶ。自己回帰モデルでは後続トークンの生成が先行トークンに依存する。並列数を増やしてページ全体の処理量が増えても、一つの文の完了が早まるとは限らない。[投機的デコードの原論文](https://arxiv.org/abs/2211.17192)。

| 段階・資源   | 変更候補                                                    | 判断に必要な観測                                                             |
| ------------ | ----------------------------------------------------------- | ---------------------------------------------------------------------------- |
| モデル準備   | 明示的な翻訳準備、ロード済みモデルの保持、0.8B選択          | ダウンロード、読み込み、初回実行を分けて測る。常駐によるメモリ消費も記録する |
| 入力処理     | トークン数による分割、短文のまとめ、共通prefixの再利用      | 入力処理時間の割合。文字数とトークン数は一致しない                           |
| 訳文生成     | PLaMo 0.8B、適切な量子化、GPUバッチ、投機的デコード         | 出力トークン数と生成時間。途中で打ち切って速く見せない                       |
| KVキャッシュ | context容量、Attention実装、必要ならKV量子化                | キャッシュ容量、実際のカーネル、GPUメモリ不足の有無                          |
| 通信・描画   | 既存の60ms通知間隔を評価し、同じフレームのDOM更新をまとめる | メッセージ数、転送文字数、Long Task、描画時刻。最初と最後の出力は遅らせない  |

### 小型化と量子化

0.8Bは既存の設定で選べるため、モデル変更を許容できる場合の最小の比較対象になる。ただし、パラメーター数の比率を速度倍率として扱わない。文脈、固有名詞、否定、数字、やさしい日本語での品質差を見て決める。

量子化は重みを少ないビット数で保存する方式だ。読み出すデータ量を減らせる一方、復元処理や対応カーネルの性能によっては遅くなる。現行Q4_K_Mに対するQ3_K_MとQ4_0の比較は、同一モデルで行う。Q4_K_Mにも異なる精度のテンソルが含まれるため、モデル全体を単純な「4bit」として速度を計算しない。[PLaMo 2B GGUF](https://huggingface.co/pfnet/plamo-3-translate-2b-GGUF)。

PLaMo 2Bは24層・Query 24ヘッド・KV 4ヘッド、0.8Bは16層・Query 16ヘッド・KV 1ヘッドだ。ともに2048トークンのSWAと、8層周期のglobal attentionを使う。2Bは既にGQA、0.8BはMQAを採用している。これらはAttentionの計算結果の保存量を減らす構造だ。

PLaMoのAttention構造は配布モデルに組み込まれている。共有するKVヘッドを増減するGQA/MQAや、見る範囲を制限するSWAは、拡張の設定を追加するだけで別構造へ変更できるものではない。現行の`swa_full: true`はキャッシュ確保の設定で、モデルの入力上限を拡張するものでもない。[2Bの設定](https://huggingface.co/pfnet/plamo-3-translate-2b/blob/main/config.json)、[0.8Bの設定](https://huggingface.co/pfnet/plamo-3-translate-0.8b/blob/main/config.json)。

FlashAttentionはAttention計算のメモリ転送を減らす方式だ。原論文の学習時の速度倍率を短い翻訳の推論へ転用しない。固定したllama.cppのWebGPUにはFlashAttentionと量子化KVの実装があるが、今回、実行時の有効状態は確認していない。[固定版のWebGPU実装](https://github.com/ggml-org/llama.cpp/blob/7d7f0287530bc8981690f361d8c1627dbae1c99a/ggml/src/ggml-webgpu/ggml-webgpu.cpp)。実際の有効状態をログで確認した後、長い入力で入力処理時間を比較する。[FlashAttention原論文](https://arxiv.org/abs/2205.14135)。

### 投機的デコード

小さいモデルが複数トークンを先に提案し、大きいモデルがまとめて検証する方式だ。正しい検証とサンプリングを実装すれば、対象モデルの出力分布を保ちながら高速化できる。しかし、提案の採用率が低い場合や、小さいモデルの実行が重い場合には得をしない。[原論文](https://arxiv.org/abs/2211.17192)、[llama.cppの実装方式](https://github.com/ggml-org/llama.cpp/blob/master/docs/speculative.md)。

PLaMo 0.8Bを2Bの補助モデルにする案は実験候補だ。名前が同系列でも、tokenizerのID・特殊トークン・停止条件が一致するか、SWAの状態を巻き戻せるか、固定したwllamaから機能を呼べるかの確認が必要になる。2モデル分のメモリとGPU競合も増える。検証もChrome内で行い、まず1要求について採用率と処理時間を測る。wllama側の対応が必要なら実装量を見積もり、現在の設定調整より優先する価値があるか判断する。ネイティブ実行の速度を採用根拠にはしない。

原文から次の出力を推測するn-gram方式は、原文と出力が一致しやすい処理に適する。英日翻訳では語順と文字体系が変わるため、コードや英文の書き換えで得られた効果を期待値にしない。数値や固有名詞の多い文章に限って検証する案にとどめる。

## このリポジトリで試す順序

### 1. 長段落とGPU並列数を別々に比較する

長段落の分割片を別ジョブにすると、他に翻訳対象が少ないページでもGPUの空き枠を使える。ただし、ページ全体から無制限に投入すると選択翻訳を待たせる。既存の優先順位と投入上限を使い、完成片を番号で保持して先頭から連続した範囲だけ表示する案にする。

並列数は2枠と4枠から比較する。現在のページ側の先読み上限は4件なので、4枠すべてで実行すると次の組の待機分がなくなる。並列数だけを変える比較と、先読み上限も調整する比較を分け、通信による補充待ちをGPUの処理時間と混同しない。一つの要求が使えるcontext容量を維持する比較と、総メモリ上限を維持する比較を分ける。合計8192のまま枠数だけ増やすと、各要求が使える容量が変わり得る。入力トークンと出力用の余裕を実際に確認する。

現在のwave方式は、短い段落が終わっても長い段落を待つ。一方、空いた枠へすぐ新しい入力を補充すると、そのprefillが進行中のdecodeを遅らせる可能性がある。まず画面内の優先順位を保ちながら似た長さを組み合わせる案を比較する。continuous batchingを指定済みでも、アプリがwaveを待っていれば途中補充は起きない。[scheduler.ts](../../features/translate/scheduler.ts)。

### 2. 完成済みの訳文と重複要求を先に処理する

現在の`translate()`は`scheduleTranslation()`の実行枠を取得してから結果キャッシュを調べる。ヒットしていても長い翻訳の終了を待つ。キャンセル状態を確認したうえで、キューへ入る前にもキャッシュを調べる案を推す。キュー実行時の再確認は待機中に別要求が結果を保存する場合に必要だ。[engine.ts](../../features/translate/engine.ts)。

次に、同じキャッシュキーの実行中要求を共有する。現在は同じwaveの2件が同時にキャッシュを調べると、両方が未保存と判定して推論できる。共有処理には、各呼出元への途中出力、個別キャンセル、最後の利用者が離れた際の推論停止、失敗結果を保存しない処理が必要になる。

最初の変更先はブラウザ側の`engine.ts`とテストに絞る。実行中要求の共有では`engine.ts`、`scheduler.ts`と、それぞれのテストが関係する。キャッシュキーに含まれるプロンプト版、実行方法、モデル、翻訳先、原文は維持する。原文の空白や句読点を勝手に正規化して、異なる入力を同一視しない。

### 3. Chrome内でPLaMoの設定を比較する

基準は現在のPLaMo 2B・Q4_K_M・GPU 2枠とする。同じGGUF、プロンプト、入力、出力上限を固定し、分割片の並列化とGPU枠数を別々に比較する。入力処理と生成の時間に加えて、ページ操作から表示までの時間を測る。

その後、PLaMo 2Bの別量子化とPLaMo 0.8Bを別々に比較する。どちらもPLaMoをChrome内で使う条件は満たすが、現在の2Bと訳文品質が同じとは限らない。品質差が許容できるかを判断する材料として扱い、既定モデルの変更や文章ごとの自動切替は行わない。

全文を0.8Bで訳してから自動的に2Bで全件訳し直す案は採らない。推論量が増え、読み始めた訳文も変わってしまう。

### 4. 計測で割合の大きかった処理を変更する

入力処理が長ければ分割サイズ、短文結合、`n_batch`と`n_ubatch`を比較する。後者は入力処理のバッチサイズであり、要求の並列枠数とは別の設定だ。[固定版llama.cppの設定](https://github.com/ggml-org/llama.cpp/blob/7d7f0287530bc8981690f361d8c1627dbae1c99a/tools/server/README.md)。生成が長ければPLaMoのサイズ・量子化・バッチを検証する。通信が長ければ途中通知の頻度、CPUが遅ければスレッド数を比較する。GPUカーネルの追加変更はプロファイルで対象処理を特定してから行う。

共通prefixのKV再利用は後回しとする。現在は独自パッチで不要な推論状態保存を停止している。`cache_prompt`を反転するだけでは意図した再利用にならない可能性があり、短い定型プロンプトで得られる節約と保存コストを比較する必要がある。[WASM最適化の記録](translation-wasm-performance.md)。

## 評価方法と採用条件

まず既存の[ブラウザ検証コード](translation-wasm-benchmark.js)を実ページの通信経路まで延ばす。モデル取得時間を含む初回と、ロード済みの通常利用、結果キャッシュがある再翻訳を別々に測る。測定用文章には公開可能な固定の文章を使う。

| 観点     | 記録する値                                               | 比較で固定する条件                                         |
| -------- | -------------------------------------------------------- | ---------------------------------------------------------- |
| 読み始め | 操作から最初の訳文、最初の段落完成、画面内全文完成まで   | 同じ画面位置、同じ段落、同じ表示方式                       |
| 全体     | 全対象の完了時間、入力処理時間、生成時間、出力トークン数 | 同じ入力、同じモデルの比較では同じGGUFハッシュとプロンプト |
| 品質     | 訳抜け、数字・否定・固有名詞・リンクの保持、途中終了     | 短文、長段落、箇条書き、技術文、やさしい日本語を区別       |
| 資源     | ピークメモリ、GPU/CPU配置、長時間利用時の変化            | ブラウザ・OS・電源状態・他アプリ負荷を記録                 |
| 操作     | 翻訳中の選択翻訳、取消、再実行、DOM更新、モデル切替      | 同じタイミングで操作し、古い結果が表示されないことを確認   |

各条件を交互に少なくとも5回測り、中央値・範囲・失敗数を残す。p95を判断する場合は別途試行数を増やす。失敗や打切りを速い結果として平均に混ぜない。モデル間ではtokenizerが異なり得るため、tokens/sだけで順位を付けず、同じ原文の完了時間と訳文品質で比較する。

採用条件として、画面内の完成時間が測定のばらつきを超えて短くなり、重大な訳抜けや取消の不具合がなく、メモリ上限内で動くことを提案する。全文の処理量だけ改善し、選択翻訳が遅くなる変更は既定にはしない。数値目標は最初の実ページ測定後に決める。

## 調査範囲と未確認事項

公開ソースと公式資料で確認できる範囲を調べた。非公開エンジンの内部実装や、あらゆるモデル・GPUの組合せを検証した調査ではない。今回の候補の速度、品質、投機的デコードのPLaMo互換性は未測定・未検証である。

文書とコードの不整合は、単独の[Ollama調査](ollama-translation-performance.md)に残っている。「現行host permissionsはGitHubとHugging Faceだけ」「localhost追加が必要」「将来Ollamaを追加する場合」という記述に対し、現在は`wxt.config.ts`でlocalhostを許可し、`ollama.ts`で接続を実装済みだ。これは古い調査時点の記述だが、同文書単体には現在との区別の注記がない。今回は実装とREADMEを基準にした。

[前回の翻訳調査](translation-performance.md)にある「直列」「途中表示未対応」「WASM未移植」は過去commitの記録と明示されているため、不整合とは扱わない。READMEと最新のWASM最適化記録には、確認範囲で明確な不整合は見つからなかった。

最初に測るのは、Chrome内のPLaMo 2Bで初めて読む長段落を翻訳したときの入力処理時間・生成時間・表示時間だ。この結果を基準に、分割片の並列化とGPUの4枠化を比較する。キャッシュの待機回避は小さな独立変更として進められるが、初めて読む文章の推論速度を上げる効果はない。
