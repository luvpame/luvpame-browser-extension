# 翻訳要求の長さを揃える変更と実機測定

以下の数値は、入力長の組み合わせを導入した時点の記録である。その後の一括翻訳・差分転送・投機的デコードなどは[追加実装の記録](translation-additional-implementation.md)に分けた。追加機能について速度の反復比較は行っていない。

2026-11-10。PLaMoをブラウザ内で使う条件を保ち、翻訳の完了を早めるため、待機中の要求の組み合わせを変更した。

採用したのは、同じGPUの組で処理する入力の長さを近づける変更である。長短が混在する15段落を実際の拡張通信で比較し、0.8Bと2Bの各6対すべてで、ページ全体と初期表示範囲の翻訳が早く完了した。初めの訳文が出るまでの時間は改善と判断しない。

モデル、Q4_K_M量子化、プロンプト、GPUの2枠、各枠4096トークン、先読み4段落は従来のままである。4枠化、先読み8段落、GPU内のトークン選択、別量子化は採用していない。[調査レポート](translation-further-performance.md)の候補を順に検証し、変更範囲を絞った。

## 比較結果

Chrome 154、Apple GPU `metal-3`、論理14コアのMacで測定した。画面サイズは1280×800。翻訳開始前に画面内にあった11段落と、ページ全体の15段落の完了を別々に記録した。完了時刻はDOMの状態を10ms周期で観測した値であり、画面への描画完了時刻ではない。

| モデル     | 初期表示範囲の完了時間の中央値・旧版 | 変更後 | 各対の短縮率の中央値 |
| ---------- | ------------------------------------ | ------ | -------------------- |
| PLaMo 0.8B | 4.37秒                               | 3.78秒 | 10.6%                |
| PLaMo 2B   | 10.15秒                              | 8.75秒 | 14.0%                |

時間の中央値と、各対で計算した短縮率の中央値は別々に集計している。後者は同じモデルで隣り合って実行した旧版・変更後の時間から計算した値である。使用順は旧→新、新→旧を交互にした。モデルごとに6対、合計24試行・360要求を測り、失敗は0件だった。[比較結果JSON](translation-browser-results.json)。

| 指標                         | 0.8B・旧版   | 0.8B・変更後 | 2B・旧版      | 2B・変更後   |
| ---------------------------- | ------------ | ------------ | ------------- | ------------ |
| ページ全体の完了時間・中央値 | 4.85秒       | 4.27秒       | 11.35秒       | 9.87秒       |
| 初期表示範囲の完了時間・範囲 | 3.32〜4.71秒 | 3.00〜4.29秒 | 9.12〜11.29秒 | 8.44〜8.94秒 |
| 最初の訳文まで・中央値       | 124ms        | 128ms        | 308ms         | 313ms        |
| 1試行の出力トークン数        | 353          | 353          | 365           | 365          |

モデルごとに、旧版と変更後の訳文は全試行で完全に一致した。出力上限は従来どおり2048で、終了理由が`stop`であることを確認した。途中で打ち切った結果や、完成済み訳文キャッシュによる省略を速い結果として数えていない。入力のKVキャッシュも全要求で未使用だった。

別の操作確認では、選択翻訳の取消がnativeで`AbortError`となり、その後の異なる原文がキャッシュを使わず正常に生成されることを確認した。証拠はJSONの`selectionSmoke`に含めた。

0.8Bではこの比較の前に旧→新の順で5対を測り、全対で完了時間が短縮した。端末の変動が大きかったため、上の表には順序を入れ替えた追加6対を使った。最初の5対もJSONの`initial08b`へ残している。

## 実装と待ち合わせ時間

従来は待機中の要求を優先度・待機順に2件ずつ組み合わせていた。短い翻訳が先に終わっても、同じ組の長い翻訳が終わるまで次の組を開始しない。

変更後も、各組の先頭は優先度と待機順を保つ。追加候補は、待機列の先頭に残った要求と同じモデル・優先度が続く範囲から選ぶ。その範囲で、実行する組の先頭と入力文字数が近い要求を組み合わせる。別モデルの待機要求を越えず、長さの差が同じ場合と、サイズが指定されていない場合は待機順を保つ。[scheduler.ts](../../features/translate/scheduler.ts)。

入力文字数は翻訳の長さを見積もるための近似であり、正確なトークン数や生成時間ではない。CPUとOllamaは1件ずつ実行するため、この組み合わせ処理で順番は変わらない。[engine.ts](../../features/translate/engine.ts)、[schedulerのテスト](../../features/translate/scheduler.test.ts)。

nativeの開始・完了通知でも、組み合わせの変更を確認した。0.8Bの最初の対では段落番号を0から数えると、旧版の`[1,2]`と`[3,4]`が、変更後は`[1,3]`と`[2,4]`になった。2件の組ごとに完了時刻の差を求め、その値を合計した。この試行の合計は旧版1379ms、変更後397msだった。この値はGPUの空転時間の直接測定ではなく、要求の完了通知から求めた待ち合わせの目安である。

選択翻訳の優先、実行中の組を終えてから次を始める動作、取消後にnative処理の終了を待つ動作は維持した。最古の要求を先頭にするため、長さを揃える目的で古い要求を待たせ続けることも避けている。

## 採用しなかった候補

| 候補                      | 検証範囲と判断                                                                                   |
| ------------------------- | ------------------------------------------------------------------------------------------------ |
| GPU4枠・各枠4096・先読み4 | 0.8Bで各5回。初期表示範囲の完了は中央値5.07秒から5.18秒となり、改善を確認できなかった            |
| GPU4枠・先読み8           | 0.8Bで各5回。4枠を埋めても初期表示範囲は5.01秒から5.29秒となり、採用しなかった                   |
| GPU内のトークン選択       | 固定nativeが受け取れる設定を使って試運転した。採用を裏づける改善を確認できず、設定は残していない |
| 0.8BのQ4_0量子化          | 公式GGUFで試運転した。継続比較や品質の採用判断までは進めず、Q4_K_Mを維持した                     |

4枠の候補には待機状態から先頭1件を開始する段階起動も含めた。要求ごとの入力処理・生成時間も伸び、枠数の増加が完了時間の短縮につながるとは確認できなかった。4枠候補の全試行もJSONの`rejected`に保存した。GPU内のトークン選択とQ4_0は試運転だけであり、確定した性能差として扱わない。

## 再実行する方法

計測用のMV3拡張は本物のcontent controller、background、offscreen、engineを使う。計測用Wllama wrapperはusageとnative timingsを非同期で記録する。配布する拡張にはこのwrapperや診断メッセージを含めない。[生成スクリプト](../../scripts/bench-browser-translation.ts)、[固定fixture](../../scripts/translation-benchmark/fixture.html)。

1. 比較対象のGGUFを用意し、次のコマンドで検証用拡張を生成する。

```sh
bun scripts/bench-browser-translation.ts selfcheck --model-file /path/to/plamo-0.8b-Q4_K_M.gguf
bun scripts/bench-browser-translation.ts serve --model-file /path/to/plamo-0.8b-Q4_K_M.gguf
```

2. 専用のChromeに`/tmp/luvpame-translation-benchmark/baseline`と`current`を読み込む。画面サイズを1280×800に揃える。
3. `http://127.0.0.1:8817/?variant=baseline`と`?variant=current`で`Run benchmark`を実行する。別の条件へ移る前に`Release GPU`を押す。
4. 最初の各1回を試運転として分ける。その後は旧→新、新→旧を交互に各6回測り、結果を保存する。

モデル準備とウォームアップは計時に含めない。各試行の前にoffscreenを閉じて作り直すため、結果キャッシュは再利用されない。実行中のGPUモデルを一つにするため、別の条件の翻訳を同時に実行しない。

2Bでは生成と配信の両コマンドに`--model 2b --model-file /path/to/plamo-2b-Q4_K_M.gguf`を指定する。別量子化を調べる場合は`--candidate-model-file`で変更後のGGUFを分けられる。モデルはSHA-256別のURLで保存・配信し、別ファイルのキャッシュを誤って再利用することを避ける。

結果は`/tmp/luvpame-translation-benchmark/results/`に保存する。GPU配置、native完了、キャッシュ未使用、保存成功を確認し、失敗した試行も原因とともに記録する。モデルと3ソースのSHA-256を含める。0.8Bの今回の測定はソースhash記録の追加前だったため、JSONには生成したJSのhashを別途残した。

基準commitは`08a37fc2e0c743ddc1c4a899c69f835cc77b7da0`。この記録の測定時はengine・scheduler・contentの3ソースを差し替え、プロンプト、通信処理、SDK、WASMを共通にした。現在の比較ツールは通信・設定処理も含めて旧版を復元する。SDKとWASMは引き続き共通であり、アプリケーションの処理を比較するツールである。記録のhashは測定時のソースと生成物に対応する。

## 適用範囲と未確認事項

Apple GPU一台と固定15段落の結果であり、ページや端末を問わず同じ短縮率になるとは判断しない。共有端末上の変動は大きく、0.8Bの測定では短い検査処理が重なった可能性もある。すべての値と順序を残し、外れた試行だけを除外していない。

GPUカーネル単位の律速とピークGPUメモリは測定していない。今回短縮したのは要求の組み合わせによる待ち合わせであり、LLMの一トークン当たりの計算を速くした変更ではない。別GPU、互換WASM、長時間の連続利用、置換表示での速度、やさしい日本語での速度は未測定である。選択翻訳の応答時間を旧版と比較する測定も行っていない。

既存の[Ollama調査](ollama-translation-performance.md)には、実装済みのlocalhost権限と接続処理を将来の作業として扱う記述が残る。実装は現行コードとREADMEに従った。参照したSakuttoのSWAコメントと枠数の食い違いは、[調査レポート](translation-further-performance.md)へ記載した。今回、これらの過去資料の本文は変更していない。
